# 四节点 Kubernetes 集群部署方案

租 4 台云主机，角色分离：**机器 1 = 控制节点**，**机器 2、3 = 业务 Worker**，**机器 4 = 数据节点**。架构更清晰，便于运维与答辩说明。

---

## 一、节点角色与整体分工

| 机器 | 角色 | 主要职责 | 说明 |
|------|------|----------|------|
| **Node1** | K8s 控制节点 | 仅跑控制面（apiserver、etcd、scheduler、controller-manager）或 K3s server | **用配置最差的机器（如 2 核 2 G）**，不跑业务与数据 |
| **Node2** | 业务 Worker | 跑所有无状态业务：Gateway、7 个微服务、前端的副本 | 与 Node3 通过反亲和分摊副本（如 2 核 4 G） |
| **Node3** | 业务 Worker | 同上，与 Node2 共同承担业务负载 | 单台宕机时另一台副本继续服务 |
| **Node4** | 数据节点 | 跑所有有状态与可观测：MySQL、Nacos、ES、MinIO、PG、Prometheus、Grafana、Jaeger、Loki | **用配置最好的机器（如 4 核 8 G）**；Promtail 见下文，需在 Node2/Node3 采集业务日志 |

**架构特点**：控制与数据分离、业务双 Worker 高可用；控制节点用最差配置、数据节点用最好配置。

---

## 二、高可用如何体现

- **业务层**：Gateway、7 个微服务、前端均 **Deployment 2 副本 + podAntiAffinity**，副本分布在 Node2 与 Node3。任意一台业务 Worker 宕机，另一台仍有副本，业务可继续访问。
- **入口**：Gateway 2 副本在 Node2/Node3，前接负载均衡或 Ingress，入口高可用。
- **数据层**：MySQL、Nacos、ES、MinIO、PG 单实例 + PVC 部署在 Node4，数据可靠；Node4 宕机则依赖数据的接口不可用，节点恢复后 Pod 挂盘重启即恢复。

---

## 三、各节点部署清单（每个节点应部署什么）

### Node1（仅控制节点）

| 类别 | 组件 | 说明 |
|------|------|------|
| **系统** | K8s Control Plane（kube-apiserver、etcd、scheduler、controller-manager）或 K3s server | 仅此节点跑控制面，不部署业务或数据类 workload |

**建议**：给 Node1 打 taint（如 `node-role.kubernetes.io/control-plane:NoSchedule`），避免业务 Pod 被调度上去，保持「纯控制节点」。

---

### Node2（业务 Worker）

| 类别 | 组件 | 部署方式 | 说明 |
|------|------|----------|------|
| **系统** | Kubelet + kube-proxy（或 K3s agent） | Worker | 只跑业务 Pod |
| **可能部署** | **Gateway** | Deployment 2 副本 + 反亲和 | Node2、Node3 各 1 副本 |
| **可能部署** | **user-service** | Deployment 2 副本 + 反亲和 | 同上 |
| **可能部署** | **content-service** | Deployment 2 副本 + 反亲和 | 同上 |
| **可能部署** | **ai-service** | Deployment 2 副本 + 反亲和 | 同上 |
| **可能部署** | **interaction-service** | Deployment 2 副本 + 反亲和 | 同上 |
| **可能部署** | **file-service** | Deployment 2 副本 + 反亲和 | 同上 |
| **可能部署** | **search-service** | Deployment 2 副本 + 反亲和 | 同上 |
| **可能部署** | **前端** | Deployment 1 或 2 副本 | 单副本时可偏好 Node2 或 Node3；2 副本则 Node2+Node3 各 1 |

**Node2 职责**：只跑无状态业务（镜像见 `docs/容器化与任务书符合性.md`）。与 Node3 共同承担全部业务流量，一台宕机另一台副本继续服务。

- **Promtail**：用 **DaemonSet** 在 Node2 上跑 1 个 Promtail Pod，用于**采集本节点**上业务 Pod 的日志文件（或容器 stdout），并推送至 Loki。详见下文「Promtail 部署说明」。

---

### Node3（业务 Worker）

| 类别 | 组件 | 部署方式 | 说明 |
|------|------|----------|------|
| **系统** | Kubelet + kube-proxy（或 K3s agent） | Worker | 只跑业务 Pod |
| **可能部署** | **Gateway** | Deployment 2 副本 + 反亲和 | Node2、Node3 各 1 副本 |
| **可能部署** | **user / content / ai / interaction / file / search** | 各 2 副本 + 反亲和 | 与 Node2 分摊 |
| **可能部署** | **前端** | Deployment 1 或 2 副本 | 同上 |

**Node3 职责**：与 Node2 对称，只跑无状态业务。不跑数据库、不跑可观测。

- **Promtail**：DaemonSet 在 Node3 上同样跑 1 个 Promtail Pod，采集本节点业务日志并推送 Loki。

---

### Node4（数据节点）

| 类别 | 组件 | 部署方式 | 说明 |
|------|------|----------|------|
| **系统** | Kubelet + kube-proxy（或 K3s agent） | Worker | 只跑有状态与可观测 |
| **固定部署** | **MySQL** | StatefulSet + nodeSelector=node4 + PVC | 业务主库 |
| **固定部署** | **Nacos** | Deployment/StatefulSet + nodeSelector=node4 + PVC | 配置中心 + 注册中心 |
| **固定部署** | **Elasticsearch** | StatefulSet + nodeSelector=node4 + PVC | 全文检索 |
| **固定部署** | **MinIO** | Deployment + nodeSelector=node4 + PVC | 对象存储 |
| **固定部署** | **PostgreSQL（pgvector）** | StatefulSet + nodeSelector=node4 + PVC | 向量库 / RAG |
| **固定部署** | **Prometheus** | Deployment + nodeSelector=node4 + PVC | 指标采集与存储 |
| **固定部署** | **Grafana** | Deployment + nodeSelector=node4 | 看板，可对外暴露 |
| **固定部署** | **Jaeger** | Deployment + nodeSelector=node4 | 链路追踪 |
| **固定部署** | **Loki** | Deployment + nodeSelector=node4 + PVC | 日志存储 |
| **固定部署** | **Promtail**（可选在 Node4 也跑一份） | DaemonSet 或 nodeSelector=node4 | 若需采集 Node4 上 MySQL/Nacos 等日志，可在 Node4 也跑 1 个 Promtail |

**Node4 职责**：所有数据库与中间件 + 可观测性（不含「必须在 Node2/Node3 跑的 Promtail」）。业务 Pod 不调度到 Node4。数据与监控集中，便于备份与扩盘。

---

### Promtail 部署说明（为什么要放在 Node2、Node3 上采集）

**Promtail 做什么**：从**本机**读取日志文件（或容器标准输出落盘后的文件），然后推送到 Loki。它只能读到**自己所在节点**上的文件，读不到其他节点磁盘上的内容。

**日志在哪**：业务 Pod（Gateway、7 个微服务、前端）跑在 **Node2 和 Node3** 上。这些 Pod 的日志要么写进挂载到该节点的 volume（如 hostPath、或你配置的 LOG_PATH 对应目录），要么是容器 stdout 被 kubelet 写到该节点的 `/var/log/pods/` 等路径。也就是说，**业务日志物理上在 Node2、Node3 的磁盘上**。

**结论**：  
- 若 Promtail **只放在 Node4**，它只能采集 Node4 上的日志（如 MySQL、Nacos 的日志），**采不到 Node2/Node3 上业务服务的日志**。  
- 所以 **Promtail 要放在 Node2、Node3 上**（通常用 **DaemonSet**：Node2、Node3 各跑一个 Promtail Pod），每个 Promtail 只采集自己所在节点的日志并推 Loki。  
- 若也要采集 Node4 上中间件/可观测的日志，可在 Node4 再跑一个 Promtail（DaemonSet 会自然在 Node4 也起一个），或单独给 Node4 部署一个 Promtail。

**推荐**：Promtail 用 **DaemonSet** 部署，不设 nodeSelector 限制（或只排除 Node1），这样 Node2、Node3、Node4 上各有一个 Promtail，各自采集本节点日志，统一推送到 Node4 上的 Loki。

---

### 汇总：按组件看落在哪台

| 组件 | Node1（控制） | Node2（业务） | Node3（业务） | Node4（数据） |
|------|---------------|---------------|---------------|---------------|
| 控制面 | ✓ 唯一 | — | — | — |
| Gateway | — | 1 副本 | 1 副本 | — |
| user / content / ai / interaction / file / search | — | 1+ 副本 | 1+ 副本 | — |
| 前端 | — | 1 副本（或与 Node3 各 1） | 1 副本（或与 Node2 各 1） | — |
| MySQL、Nacos、ES、MinIO、PG | — | — | — | ✓ 固定 |
| Prometheus、Grafana、Jaeger、Loki | — | — | — | ✓ 固定 |
| **Promtail** | — | ✓ DaemonSet 1 个 | ✓ DaemonSet 1 个 | ✓ DaemonSet 1 个（可选，采 Node4 日志） |

## 四、用 K8s 如何实现

1. **控制面**：仅在 Node1 上执行 `kubeadm init` 或安装 K3s server；Node2、Node3、Node4 执行 `kubeadm join` 或 K3s agent，并指向 Node1。
2. **节点标签**：  
   - Node1：`node=node1` 或 `node-role.kubernetes.io/control-plane=`  
   - Node2：`node=node2`  
   - Node3：`node=node3`  
   - Node4：`node=node4`
3. **业务只跑在 Node2/Node3**：所有业务 Deployment（Gateway、7 个微服务、前端）加 **nodeSelector: node in [node2, node3]** 或 **affinity** 限定在 Node2、Node3；replicas ≥ 2 + **podAntiAffinity** 打散到两台。
4. **数据与可观测只跑在 Node4**：MySQL、Nacos、ES、MinIO、PG、Prometheus、Grafana、Jaeger、Loki、Promtail 的 Deployment/StatefulSet 均加 **nodeSelector: node=node4**，并配置 PVC（Node4 需足够存储或云盘）。
5. **入口**：Ingress 或云厂商 LB 后端指向 Node2、Node3 上 Gateway 的 NodePort/Service，实现入口高可用。

## 五、K3s 集群检查（部署后验证）

在 **Node1（控制节点）** 上执行（K3s 会把 kubeconfig 写在 `/etc/rancher/k3s/k3s.yaml`，需用 root 或加 sudo）：

```bash
# 使用 K3s 自带的 kubectl（Node1 上）
sudo k3s kubectl get nodes
```

若在**本机**用 kubectl，先把 Node1 上的 kubeconfig 拷到本机（或本机已安装 kubectl 并配置 KUBECONFIG 指向 Node1）：

```bash
# 1. 看 4 个节点是否都为 Ready
kubectl get nodes

# 2. 看节点详情（IP、角色、标签）
kubectl get nodes -o wide

# 3. 看节点标签（应有 node=node1/node2/node3/node4，控制节点有 control-plane）
kubectl get nodes --show-labels

# 4. 看系统 Pod 是否都 Running（kube-system 等）
kubectl get pods -A
```

**预期结果**：

- `kubectl get nodes`：4 个节点状态均为 **Ready**。
- 节点标签：Node1 有 `node-role.kubernetes.io/control-plane`（或你打的 `node=node1`），Node2/3/4 有 `node=node2`、`node=node3`、`node=node4`（若已按方案打过标签）。
- `kubectl get pods -A`：`kube-system` 下无大量 CrashLoopBackOff，核心组件 Running 即可继续部署业务。

## 五.1 集群 Ready 后的下一步（按顺序做）

1. **给 4 个节点打标签 + Node1 打污点**  
   - 在 Node1 或已配置 kubeconfig 的操作机上执行：  
     - `deploy/node1/label-taint.sh`：为控制节点打 `node=node1` 和 `NoSchedule` 污点。  
     - 编辑 `deploy/label-nodes.sh`，把 `NODE2_NAME`、`NODE3_NAME`、`NODE4_NAME` 填成 `kubectl get nodes` 里对应节点名（先 `kubectl get nodes -o wide` 根据 IP/机型区分哪台是 Node2/3/4），再执行该脚本，为三台 Worker 打 `node=node2`、`node=node3`、`node=node4`。  
   - 验证：`kubectl get nodes --show-labels` 应看到 4 台都有对应 `node=node1`～`node=node4`。

2. **准备 Node4 数据盘与存储**（第一步）
   - **云控制台**：为 Node4 实例挂载一块云盘并连接到实例。
   - **在 Node4 上**：执行 `deploy/node4/setup-data-disk.sh`（默认使用 `/dev/vdb`，否则 `DATA_DISK=/dev/vdc ./setup-data-disk.sh`），完成格式化、挂载到 `/mnt/data` 并写入 `/etc/fstab`。若希望 K3s 的 PVC 都落在该盘，按脚本末尾「可选」步骤把数据盘绑定到 `/var/lib/rancher/k3s/storage`。
   - **验证**：K3s 默认带 `local-path` StorageClass，`kubectl get storageclass` 可见；有状态 workload 使用 `nodeSelector: node=node4` 即可使 PVC 落在 Node4。

3. **部署顺序**
   - **第二步：先 Node4**：MySQL、Nacos、ES、MinIO、PG、Prometheus、Grafana、Jaeger、Loki、Promtail 等（nodeSelector=node4 + PVC）。需为每个组件准备 K8s 清单（Deployment/StatefulSet + Service + PVC，或 Helm），并统一加 `nodeSelector: { node: node4 }`、`storageClassName: local-path`（需持久化的）。
   - **第三步：再业务**：Gateway、7 个微服务、前端（nodeSelector 限制在 Node2/Node3，2 副本 + 反亲和）；镜像需先构建并推送到可拉取的仓库（如 ACR），Nacos 地址等通过 ConfigMap/环境变量注入。
   - **第四步：最后入口**：云厂商 LB 或 Ingress 指到 Node2/Node3 上 Gateway 的 NodePort/Service。

**第二步清单（Node4 中间件，建议部署顺序）**：MySQL → Nacos → ES、MinIO、PostgreSQL(pgvector) → Prometheus、Grafana、Jaeger、Loki → Promtail（DaemonSet 或 nodeSelector=node4）。业务依赖 Nacos 与各数据库，故 Nacos 和 MySQL 宜最先就绪。仓库中 `infrastructure/` 下有 MySQL/Postgres 初始化 SQL、Prometheus/Loki/Promtail 配置等，可复用到 K8s 的 ConfigMap 或 init 容器。

## 六、高可用演示建议

- **模拟 Node2 宕机**：关 Node2，流量由 Node3 上副本承接，业务可访问；恢复后 Pod 重新调度。
- **模拟 Node3 宕机**：同理，Node2 上副本继续服务。
- **模拟 Node4 宕机**：依赖数据库/ES/MinIO 的接口不可用；Node4 恢复后，有状态 Pod 挂盘重启，数据不丢。
- **模拟 Node1 宕机**：调度暂停，已跑在 Node2/Node3 的 Pod 仍可服务；Node1 恢复后集群恢复正常。

按上述分配，**机器 1 = 控制，机器 2/3 = 业务 Worker，机器 4 = 数据节点**，架构清晰、职责单一，便于答辩与后续扩展。
