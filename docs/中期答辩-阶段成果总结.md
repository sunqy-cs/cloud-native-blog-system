# cloud-native-blog-system 中期答辩阶段成果总结

## 一、项目目标与阶段定位

本项目目标是构建一个可部署、可扩展、可观测的云原生博客系统，采用前后端分离与微服务架构，落地到 K3s 集群环境，形成从开发、容器化、部署到运行观测的完整闭环。  
当前阶段定位为：完成核心架构搭建、基础部署能力、业务主链路可用，以及关键数据迁移与验证。

## 4. 各微服务职责说明（答辩重点）

为避免“单体系统职责耦合、扩展困难”，本项目将核心能力拆分为 Gateway + 7 个后端微服务。各服务职责如下：

### 4.1 gateway-service（网关服务）

- **定位**：系统统一入口，负责路由转发与基础网关治理。
- **核心职责**：
  - 接收来自前端或外部入口（如 ALB）的请求；
  - 按路径规则将请求分发到 user/content/file/search/interaction/ai 等服务；
  - 承担鉴权透传、统一跨域、统一错误处理等网关层通用逻辑。
- **价值**：对外隐藏内部服务拓扑，降低前端与后端服务的耦合，便于后续灰度与限流扩展。

### 4.2 user-service（用户服务）

- **定位**：用户域核心服务，管理“谁在使用系统”。
- **核心职责**：
  - 用户注册、登录、身份认证与基础资料管理；
  - 维护用户画像类数据（如昵称、头像、个人信息等）；
  - 为其他服务提供用户身份与用户信息的基础查询能力。
- **价值**：将身份与账号体系独立，避免内容、互动等服务重复维护用户逻辑。

### 4.3 content-service（内容服务）

- **定位**：业务核心服务，管理“文章/内容本身”。
- **核心职责**：
  - 文章草稿保存、发布、编辑、删除与详情查询；
  - 内容标签、专栏、可见性、创作声明等元信息管理；
  - 对接 Postgres 向量表能力，支撑知识库切片/向量相关场景；
  - 对接 search-service 进行内容检索索引协同。
- **价值**：承载博客系统主业务流程，是发布与管理链路的核心中台。

### 4.4 file-service（文件服务）

- **定位**：统一文件与媒体资源管理服务。
- **核心职责**：
  - 图片/附件上传、访问地址生成与文件元数据管理；
  - 对接 MinIO 对象存储，屏蔽底层存储细节；
  - 为内容发布、封面上传、编辑器插图等场景提供文件能力。
- **价值**：将二进制资源管理与业务逻辑解耦，提升扩展性与可维护性。

### 4.5 search-service（搜索服务）

- **定位**：全文检索与搜索编排服务。
- **核心职责**：
  - 对接 Elasticsearch 完成内容索引与查询；
  - 提供关键词检索、结果排序、分页返回等能力；
  - 支持通过重建接口从业务库回灌索引，保障检索一致性。
- **价值**：独立搜索能力，避免在内容服务中混入复杂检索逻辑，便于后续扩展搜索策略。

### 4.6 interaction-service（互动服务）

- **定位**：用户行为与互动数据管理服务。
- **核心职责**：
  - 点赞、评论、收藏等互动行为的写入与统计；
  - 提供内容维度互动计数（如点赞数、评论数）；
  - 支撑创作者中心的数据看板与互动相关展示。
- **价值**：将高频互动写入从内容主链路拆分，降低内容服务压力，便于后续高并发优化。

### 4.7 ai-service（AI 能力服务）

- **定位**：统一 AI 能力封装服务。
- **核心职责**：
  - 对接大模型能力，提供标题生成、摘要提取、标签建议、封面建议等功能；
  - 为发布页“一键生成”与创作辅助提供标准化接口；
  - 为知识库相关智能能力（如 RAG 场景）提供扩展入口。
- **价值**：将模型接入与 Prompt 逻辑集中管理，降低业务服务对具体模型厂商的耦合。

### 4.8 服务协作关系（可用于答辩讲解）

- **发布链路**：前端 -> Gateway -> content-service（保存/发布） + file-service（上传封面/图片） + ai-service（生成辅助）。
- **检索链路**：前端 -> Gateway -> search-service（ES 查询） -> content-service（补全内容摘要信息）。
- **互动链路**：前端 -> Gateway -> interaction-service（点赞/评论/收藏） -> content-service（展示统计）。
- **用户链路**：前端 -> Gateway -> user-service（登录鉴权/资料）。

通过以上拆分，系统实现“按领域拆职责、按能力做治理”的云原生微服务架构，支撑后续独立扩容与演进。

## 5. 前端架构设计特色

本项目前端采用“页面层 - 业务层 - 接口层”的分层设计，以 Vue3 + TypeScript 为基础，突出可维护、可扩展与多服务协同能力，主要体现在以下方面：

- **分层解耦的代码组织**：`views` 承载页面编排，`components` 负责可复用 UI 组件，`api` 统一封装请求，`stores` 管理全局状态。通过分层让页面逻辑、数据请求、状态管理职责清晰，降低耦合。
- **统一请求网关与接口治理**：前端统一通过 `/api` 访问后端，由请求封装层集中处理 token 注入、错误提示、401 失效跳转等通用逻辑，避免各页面重复实现，提高一致性。
- **路由驱动的业务流设计**：采用 Vue Router 组织推荐页、创作者中心、发布页等核心流程，基于路由参数承载“新建/编辑”等上下文，实现页面状态与 URL 一致，便于分享、回退与刷新恢复。
- **状态管理与页面状态协同**：通过 Pinia 管理用户登录态、基础资料等跨页面状态；页面内部使用组合式 API 管理临时状态与交互状态，形成“全局状态最小化、局部状态就近管理”的架构原则。
- **富文本编辑器能力模块化**：发布页围绕 Vditor 做二次封装，将工具栏行为、目录解析、内容同步、图片上传等能力模块化，兼顾技术写作场景与后续功能迭代（如模板、快捷键、自动保存）。
- **AI 能力前端编排**：将标题生成、摘要提取、标签建议、封面生成与一键生成等 AI 功能统一接入写作工作流，通过标准化接口与状态反馈（loading/结果回填），实现“人机协同创作”体验。
- **可部署与运行一致性**：前端采用容器化交付（Vite 构建 + Nginx 托管），与后端微服务共享统一发布方式，配合 Gateway/ALB 实现线上访问路径一致，降低环境差异。

在答辩层面，可将前端架构特色概括为：以分层解耦为核心、以网关统一访问为基础、以创作工作流和 AI 编排为亮点的工程化前端架构实践。

- 高并发与故障注入场景下的压测与稳定性数据尚不充分。

## 2. 下一阶段重点

- 打通 CD 闭环：ACR 构建完成后自动触发 K3s 滚动发布。
- 完善质量门禁：补齐关键模块测试与基础 CI 校验流程。
