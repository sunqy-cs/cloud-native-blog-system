# 三节点 Kubernetes 集群部署方案（历史参考）

> **当前采用四节点方案**：机器 1 = 控制节点，机器 2/3 = 业务 Worker，机器 4 = 数据节点。详见 **[四节点集群部署方案.md](四节点集群部署方案.md)**。  
> 下文为原三节点方案，仅作参考。

租 3 台同规格云主机（建议每台 4核8G 或 4核16G），组成 1 Master + 2 Worker 的 K8s 集群。下面约定每台机器的角色与跑哪些组件。

---

## 一、节点角色与整体分工

| 节点 | 角色 | 主要职责 | 说明 |
|------|------|----------|------|
| **Node1** | Master + Worker | 控制面 + 核心中间件 + 网关 + 监控入口 | 对外入口、MySQL/Nacos、Gateway、Grafana 等 |
| **Node2** | Worker | 中间件 + 部分微服务 + 可观测 | ES、MinIO、部分 Java 服务、Prometheus/Jaeger/Loki |
| **Node3** | Worker | 中间件 + 其余微服务 + 前端 | PG、其余 Java 服务、前端、Promtail |

控制面只放 Node1，简单稳定；有状态服务分散到三台；**无状态服务必须多副本 + 反亲和**，才能体现高可用（见下文）。

---

## 二、高可用如何体现（核心）

任务书要求「验证高可用、模拟某服务实例宕机后系统能自动恢复」。高可用在本方案里体现在以下几方面。

### 2.1 无状态服务：多副本 + 跨节点分布（真正体现 HA）

- **做法**：Gateway、user、content、ai、interaction、file、search 均使用 **Deployment，replicas ≥ 2**，并配置 **podAntiAffinity**（同一 Deployment 的 Pod 尽量调度到不同节点）。
- **效果**：任意一台 Worker（Node2 或 Node3）宕机时，另一台节点上仍有该服务的副本，**业务仍可被访问**；K8s 会标记失联节点上的 Pod 为失败并在健康节点上拉起新 Pod，实现「自动恢复」。
- **入口**：Gateway 也 2 副本，一个在 Node1、一个在 Node2（或 Node1+Node3），前面用云厂商 **负载均衡** 或 **Ingress 多副本** 把流量打到两个 Gateway Pod。这样 Node1 宕机时，由 Node2 上的 Gateway 继续接流量，**入口也高可用**。

若不设多副本，每个服务只跑 1 个 Pod 且固定在某节点，则「某台机子挂了 = 该机上所有服务都挂」，只能演示「恢复后 K8s 重新调度」，无法演示「宕机期间业务不中断」，高可用体现不足。

### 2.2 有状态服务：单实例 + 持久化（数据不丢，可用性不保证）

- **做法**：MySQL、Nacos、ES、MinIO、PG 每类只跑 **单实例**，用 **PVC 持久化**，并用 nodeSelector 固定到约定节点。
- **原因**：主从/集群部署（如 MySQL 主从、ES 集群、Nacos 集群）配置和运维成本高，毕设阶段用单实例 + 持久化即可。
- **效果**：**数据高可靠**（盘在则数据在）；**可用性**上，若某节点宕机，该节点上的数据库/中间件会不可用，直到节点恢复后 Pod 重新挂盘启动。即：有状态层不做「多副本 HA」，只做「故障后自动恢复」。

### 2.3 可观测性

- Prometheus、Grafana、Jaeger、Loki、Promtail 单实例即可，宕机只影响监控与排查，不要求业务高可用。

### 2.4 小结：哪里算「高可用」

| 层级 | 是否高可用 | 方式 |
|------|------------|------|
| **入口（Gateway）** | 是 | 2 副本 + 反亲和 + 负载均衡 |
| **前端** | 可选 | 默认单副本在 Node3；要 HA 则 2 副本 + 反亲和（如 Node2+Node3） |
| **业务微服务（7 个）** | 是 | 各 2 副本 + 反亲和，分散在 Node2/Node3（或含 Node1） |
| **有状态（MySQL/Nacos/ES/MinIO/PG）** | 否（单实例） | 持久化 + 故障后自动恢复 |
| **控制面** | 否（单 Master） | Node1 宕机则调度暂停，节点恢复后恢复 |

答辩时可说：**无状态服务通过多副本与跨节点部署实现高可用；有状态服务采用单实例与持久化保证数据可靠，并通过 K8s 实现故障后自动恢复。**

## 三、各节点部署清单（每个节点应部署什么）

每个节点分两类：**固定部署**（用 nodeSelector 固定在该节点）和 **可能部署**（无状态多副本经反亲和打散后，可能有一个或多个 Pod 落在该节点）。所有业务与前端均使用**独立 Docker 镜像**（见 `docs/容器化与任务书符合性.md`）在 K8s 中以 Deployment/StatefulSet 运行。

---

### Node1（Master + 核心）

| 类别 | 组件 | 部署方式 | 说明 |
|------|------|----------|------|
| **系统** | K8s Control Plane（kube-apiserver、etcd、scheduler、controller-manager）或 K3s server | 仅 Node1 | 控制面单节点，不参与业务调度时可同时做 Worker。 |
| **固定部署** | **MySQL** | StatefulSet + nodeSelector=node1 + PVC | 业务主库，单实例。 |
| **固定部署** | **Nacos** | Deployment/StatefulSet + nodeSelector=node1 + PVC | 配置中心 + 注册中心，单实例。 |
| **固定部署** | **Grafana** | Deployment + nodeSelector=node1 | 监控看板，对外暴露。 |
| **可能部署** | **Gateway** | Deployment 2 副本 + 反亲和 | 至少 1 副本建议落在 Node1，作为主入口；另 1 副本在 Node2，实现入口高可用。 |
| **可能部署** | **Prometheus** | Deployment 1 副本 + nodeSelector=node1（或 Node2） | 可放在 Node1 与 Grafana 同机，或放 Node2。 |

**Node1 职责**：控制面 + MySQL + Nacos + Grafana +（通常）1 个 Gateway 副本。断掉则调度与核心依赖不可用，若 Gateway 有副本在 Node2，入口仍可接流量。

---

### Node2（Worker）

| 类别 | 组件 | 部署方式 | 说明 |
|------|------|----------|------|
| **系统** | Kubelet + kube-proxy（或 K3s agent） | 仅 Worker | 不跑控制面。 |
| **固定部署** | **Elasticsearch** | StatefulSet + nodeSelector=node2 + PVC | 全文检索，单实例。 |
| **固定部署** | **MinIO** | Deployment + nodeSelector=node2 + PVC | 对象存储，单实例。 |
| **固定部署** | **Prometheus** | Deployment + nodeSelector=node2 | 抓取各服务 /actuator/prometheus（若未放 Node1）。 |
| **固定部署** | **Jaeger** | Deployment + nodeSelector=node2 | 链路追踪。 |
| **固定部署** | **Loki** | Deployment + nodeSelector=node2 + PVC | 日志存储。 |
| **可能部署** | **Gateway** | Deployment 2 副本 + 反亲和 | 1 副本在 Node1，1 副本在 Node2，实现入口高可用。 |
| **可能部署** | **user-service** | Deployment 2 副本 + 反亲和 | 与 Node3 各 1 副本或按调度分布。 |
| **可能部署** | **content-service** | Deployment 2 副本 + 反亲和 | 同上。 |
| **可能部署** | **ai-service** | Deployment 2 副本 + 反亲和 | 同上。 |
| **可能部署** | **前端** | Deployment 1 或 2 副本 | 若前端 2 副本做 HA，可 Node2+Node3 各 1；单副本时可只放 Node3。 |

**Node2 职责**：ES + MinIO + 可观测（Prometheus/Jaeger/Loki）+ 部分业务与 Gateway/前端的副本。断掉后依赖 ES/MinIO 的接口不可用，Node1/Node3 上副本仍可服务其余接口。

---

### Node3（Worker）

| 类别 | 组件 | 部署方式 | 说明 |
|------|------|----------|------|
| **系统** | Kubelet + kube-proxy（或 K3s agent） | 仅 Worker | 不跑控制面。 |
| **固定部署** | **PostgreSQL（pgvector）** | StatefulSet + nodeSelector=node3 + PVC | 向量库 / RAG，单实例。 |
| **固定部署** | **Promtail** | DaemonSet 或 Deployment + nodeSelector=node3 | 采集日志推 Loki；若用 DaemonSet 则每节点一个。 |
| **可能部署** | **interaction-service** | Deployment 2 副本 + 反亲和 | 与 Node2 各 1 副本或按调度分布。 |
| **可能部署** | **file-service** | Deployment 2 副本 + 反亲和 | 同上。 |
| **可能部署** | **search-service** | Deployment 2 副本 + 反亲和 | 同上。 |
| **可能部署** | **前端** | Deployment 1 或 2 副本 | 默认至少 1 副本在 Node3（Nginx + 静态资源）；要 HA 则 Node2+Node3 各 1。 |

**Node3 职责**：PG + Promtail + 互动/文件/搜索服务及前端的副本。断掉后评论、文件、搜索、前端受影响，Node2 上业务副本仍可部分服务。

---

### 汇总：按组件看落在哪台

| 组件 | Node1 | Node2 | Node3 |
|------|-------|-------|------|
| 控制面 | ✓ 唯一 | — | — |
| MySQL | ✓ 固定 | — | — |
| Nacos | ✓ 固定 | — | — |
| Elasticsearch | — | ✓ 固定 | — |
| MinIO | — | ✓ 固定 | — |
| PostgreSQL | — | — | ✓ 固定 |
| Gateway | 1 副本（建议） | 1 副本 | — |
| user / content / ai | 可选 | 1+ 副本 | 1+ 副本 |
| interaction / file / search | — | 1+ 副本 | 1+ 副本 |
| 前端 | — | 可选（HA 时 1 副本） | ✓ 至少 1 副本 |
| Grafana | ✓ 固定 | — | — |
| Prometheus | 或 Node1 | ✓ 固定（或 Node1） | — |
| Jaeger、Loki | — | ✓ 固定 | — |
| Promtail | — | 可选 | ✓ 固定（或 DaemonSet 每节点） |

## 四、用 K8s 如何实现「跑在哪台」

1. **控制面**  
   - 使用 kubeadm 时，只在 Node1 上执行 `kubeadm init`，Node2/Node3 执行 `kubeadm join`。  
   - 使用 K3s 时，Node1 跑 `kube-server`，Node2/Node3 跑 `kube-agent` 并指向 Node1。

2. **指定节点跑指定 Pod**  
   - 给 Node1/Node2/Node3 打 label，例如：  
     `node-type=master`, `node-type=worker1`, `node-type=worker2`  
     或按用途：`node=node1`, `node=node2`, `node=node3`。  
   - 在对应 Deployment/StatefulSet 里加 **nodeSelector** 或 **affinity**，例如：  
     - MySQL、Nacos 的 Pod：`nodeSelector: node: node1`  
     - ES、MinIO：`nodeSelector: node: node2`  
     - PG、前端、Promtail：`nodeSelector: node: node3`  
   - **无状态服务**（Gateway、user、content、ai、interaction、file、search）：**replicas ≥ 2**，并配置 **podAntiAffinity**（同一 Deployment 的 Pod 尽量分散到不同节点），这样单节点宕机时仍有副本可用，才体现高可用。

3. **持久化**  
   - 每台机器为本地盘或云盘配置 StorageClass，MySQL、Nacos、ES、MinIO、PG 的 PVC 绑定到对应节点（或使用云盘不绑节点）。  
   - 若用本地盘，有状态组件的 Pod 需要固定节点（nodeSelector/affinity），否则 PVC 无法挂到别的节点。

4. **入口**  
   - Node1 上暴露 Gateway 的 Service（NodePort 或 HostPort），或在该节点装 Nginx Ingress Controller，对外 80/443，再转发到 Gateway。  
   - 若用云厂商负载均衡，可将 LB 后端指向三台节点的 NodePort，实现简单高可用。

## 五、高可用演示建议

- **模拟 Node2 宕机**：关闭 Node2 或断网。若已按第二节为无状态服务配 2 副本 + 反亲和，则 Node3（及 Node1）上仍有副本，**部分或全部接口仍可访问**；依赖 Node2 上 ES/MinIO 的接口可能报错。恢复 Node2 后，K8s 将失联 Pod 标记为失败并在健康节点上拉起新 Pod，服务恢复。
- **模拟 Node3 宕机**：同理，观察 Node2 上副本是否继续服务；恢复后看 Pod 是否重新调度。
- **模拟 Node1 宕机**：若 Gateway 仅单副本在 Node1，则整站不可达；若 Gateway 为 2 副本且 LB 指向多节点，则 Node2 上的 Gateway 仍可接流量，**入口高可用**得到体现。
- **滚动更新**：对某 Deployment 执行 `kubectl set image ...` 或发布新镜像，观察 Pod 逐个替换、请求不中断，体现**发布过程高可用**。

按上述分配，每台机器跑什么、在 K8s 里如何用 nodeSelector/affinity 固定或打散，在 YAML 里写清楚即可；无状态服务务必 **replicas ≥ 2 + podAntiAffinity**，高可用才有据可查。
